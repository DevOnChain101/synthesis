# ADR-021: One protocol (v4) and three thin surfaces: CLI, TUI, Super Agent

Status: Proposed (2026-11-14, revised: the orchestrator serves all three surfaces). Placement of Outcomes per surface needs owner decisions (plan D5, D6).
Related: ADR-015 (WSL engine over stdio), ADR-016, ADR-017, ADR-019. Specs: `docs/specs/desktop.md`, `docs/specs/events.md`, `docs/cli-palette.md`, `docs/CLI-APP.md`.

Terminology (owner, CLAUDE.md): **CLI** = the `synt` binary, whose terminal app opens with no subcommand (there is no `synt tui`); **TUI** = the terminal-style tab of the desktop app (`apps/desktop`, `tui_view/`); **Super Agent** = the desktop's "Agent" entry, "Coming soon" today. Settings: the CLI reads `synt.cli.*`, the TUI `synt.tui.*`; the Super Agent has no section yet (proposal below).

## Context

Owner direction (design section 22): keep Workspace with Sessions nested, chat primary, composer controls under the chat, **one** right-side tabbed popup for inspection, Outcomes and Decisions above low-level sessions.

Facts: `View { Tui, SuperAgent, Settings }` (`apps/desktop/src/ui.rs:29-33`); the owner said the Agent will be a different desktop design later (HANDOFF 1b), so its layout is unknown. The TUI has left panels, centre tabs `ChatTab { Chat, Diff, Terminal, Browser, Files }` (`tui_view/mod.rs:89-96`), a right panel stack that collapses to a drawer; chat is always the majority (`docs/specs/desktop.md`). View models are UI-agnostic in `synthesis-view` (`ViewState::apply(&Envelope)`, shared by the CLI and the desktop). **Today the CLI talks to its engine in process, not through the protocol**; the desktop uses the protocol only for WSL (`apps/desktop/src/remote.rs:20`); protocol 3 has an exact hello match, requests `{"id","method","params"}`, events as envelopes, asks as `ask.approval`/`ask.input` (`synthesis-app/src/proto.rs:19,71-231,308`). `notify.rs` sends ids and codes only, for governed runs only (`synthesis-app/src/notify.rs:5-9,158`), and the desktop has no notifier (`docs/UNATTENDED.md` Notifications).

## Options

A. One protocol, three thin clients, a shared view-model layer (decision below).
B. Per-surface integration (CLI calls library functions, desktop uses the protocol).
C. A new HTTP/JSON API for the Super Agent.

## Decision

Option A. B duplicates logic and hides the real boundary from tests; C adds a listener the repo has avoided (ADR-012, HARD-12).

### 1. One protocol

- **Protocol v4**: `PROTOCOL = 4`, exact match like v3 (no negotiation; surfaces and orchestrator of one install ship together; ADR-015). All surfaces use it, **the CLI included, even when the server is in the same process**: a client library `synthesis_app::outcome_client` offers the same typed calls over three transports: `InProc` (tests and headless CI only, never a production path), `Stdio` (WSL engine link), `LocalSocket` (the standalone orchestrator, ADR-017). There is no per-surface path: no surface imports `synthesis-orchestrator`.
- **Methods** (additive to v3): `orchestrator.status`, `orchestrator.enable` (explicit migration, ADR-016 item 9); `outcome.create {workspace, goal, contract_draft}`, `outcome.contract.get`, `outcome.contract.approve {version, hash}`, `outcome.start|pause|resume|cancel|ack`, `outcome.get`, `outcome.list {workspace}` (each row carries `needs_you`, below); `plan.get`; `work_item.get`; `attempt.inspect {id}`; `decision.list|get|resolve {id, expected_revision, choice, note}`; `evidence.get`; `command.status {idempotency_key}`; `events.subscribe {outcome, after_event_id}` (cursor, reconnect, pagination, redaction as `session.preview`). Every mutating method is a revision-checked command (ADR-016 item 11) and returns `applied | stale | already_resolved | denied | queued`.
- Outcome events are ordinary envelopes of the control session (additive types, `v` stays 1), so v3 consumers ignore them (`docs/specs/events.md` section 7). A `{"msg":"decision","outcome","id","revision","state"}` hint line is pushed on every decision row change to a link that asked for it (`attach {push: ["decision"]}`, see the B2 notes below), so a connected client need not poll.
- Decisions are answered by a person only; `decision.resolve` is accepted only from a surface's transport. The hostile-engine rule of v3 (an unsolicited `restarted`) extends to unsolicited command results.
- No TCP and no HTTP: stdio, in-process (tests) and the same-user local socket or named pipe with the mutual HMAC handshake of peers (`synthesis-peers/src/net.rs`).

### 2. Thin surfaces (no logic in UI)

- **Shared view-model layer.** `synthesis-view` gains `outcomes` models (outcome list with `needs_you`, plan/DAG rows, criteria table, attempts, decisions, evidence) built from protocol replies and `outcome.*` envelopes. The **inspector tab set** is defined once there: `Overview`, `Workers`, `Activity`, `Diff`, `Evidence`. Surfaces render; they never compute verdicts, states, bindings or briefs.
- **Decision brief is structured data** (ADR-019): fields `why_human`, `delta`, `alternatives[{id, name, tradeoffs}]`, `evidence_refs`, `unknowns`, `defer_consequence`, `expires_at`, `default_action = HOLD`, `binding`. No field marks a recommended or selected option. Surfaces may lay it out differently but must show every field present, must not reorder alternatives by preference, must not preselect, and must show the stale/invalidated state returned by the server. A shared renderer test ("every non-empty field appears") runs for each surface.

### 3. Per surface

| Surface | Outcomes entry | Decisions | Inspector | Status |

CLI and TUI settings only affect rendering: `synt.cli.outcomes.*`, `synt.tui.outcomes.*` (panel visible, density). Everything that changes behaviour, budgets or security is under `synt.orchestrator.*` and read from user or managed settings only (plan, "Settings split"); `synt doctor` warns about orchestrator keys found under a surface section, as it already does for CLI-only keys left under `synt.tui` (`CLAUDE.md`). A `synt.superagent.*` section is proposed for when that surface exists (plan D17).

### 4. "Needs you" signal and notifications when no surface is open

- **Durable signal.** `outcome.list` and `outcome.get` return `needs_you: {decisions_pending, blocked, verified_awaiting_ack}` (`critical` was dropped, see the B2 notes) computed from rows (Pending decisions, outcome `Blocked`, `Verified` not yet acknowledged). Any surface shows it on open; the CLI prints it at the start of `synt outcome status` and, later, in the terminal app banner. It survives restarts because it is derived from the store.
- **Push when nothing is open.** The orchestrator process sends the existing notify hook (`synt.notify`, user or managed settings, sandboxed command, ids and codes only, never text by default; `docs/UNATTENDED.md` Notifications) with new event kinds `decision.created`, `outcome.blocked`, `outcome.verified`; payload `{event, outcome_id, decision_id?, kind, reason_code, ts}`. Deduped per `(decision_id, revision)`; the existing caps apply (4 concurrent, 50 per process, `task.ended` reserve). `notify.rs` today starts only for governed runs and the interactive CLI never notifies; the orchestrator process is a governed run, so it qualifies.
- The desktop's own system notification stays a stub (`kind: "desktop"` is skipped today); the orchestrator does not depend on it. When a desktop notifier exists it is a surface feature fed by the same events.
- Payloads never carry brief text, so a notification leaks nothing a lock screen should not show.

### 5. Two surfaces on one outcome

One owner (the orchestrator process), many viewers, actions as revision-checked commands (ADR-016, ADR-019 section 5). A surface that loses a race shows the server's `already_resolved` or `stale` and refetches; it never retries with a guessed revision. Subscriptions are scoped to an outcome, resumable from `after_event_id`, and every surface treats its cache as a projection.

## Consequences

- Positive: lifecycle provable headless through the protocol (acceptance doc); surfaces are small; one change to a rule is one change.
- Negative: the CLI gains a client indirection even in process; the exact version match forces lock-step updates of the CLI, the orchestrator process and the desktop (ADR-016 matrix); TUI layout changes touch `design_tests` (browser-measured rects); Windows desktop reaches outcomes only through WSL.
- Unverified: pixel design, keyboard model, whether the right drawer can host tabs without breaking the chat >= 55% rule, the Super Agent design.

## Revisit trigger

- The owner delivers the Super Agent design (fill in section 3, row 3).
- More than about 5 open outcomes per workspace make the nested list unusable.
- A non-desktop client needs the protocol (then versioned negotiation replaces the exact match).
- Notification needs exceed ids and codes (then a reviewed redaction design).

## Implementation notes (PR-11: protocol v4, client library, view models)

- **Status of this ADR:** still Proposed as a whole; section 1 (methods, client library, hostile-engine rule) and the view-model half of section 2 are implemented, the CLI surface of section 3 is implemented (PR-13, below); the TUI and Super Agent surfaces and the terminal app's `/outcomes` are not.
- **Wire.** `PROTOCOL = 4`, exact match (a protocol 3 engine is refused, tested). New `Call` variants use the method names of section 1. Differences from the text above, on purpose: every mutating call carries `idempotency_key` and `surface` (`cli|tui|superagent`, self-asserted until the endpoint authenticates clients, PR-12); `decision.*` and `command.status` also carry `outcome` (a decision id alone does not say which outcome's store view to open); `decision.resolve` carries `brief_sha256` (the hash of the brief that was shown, required by the store) besides `expected_revision`, `choice` and an optional `note`; `events.subscribe` is one page after a cursor (`{events, next_event_id}`, 200 per page), not a push stream; `needs_you` is `{decisions_pending, blocked, verified_awaiting_ack}` (no `critical`: nothing defines it yet; `verified_awaiting_ack` is "the outcome is `verified`").
- **Server.** `synthesis_app::outcome_service` reads the store (`Reader`) and queues commands (`Store::enqueue_command`); it never applies one, so a mutating call answers `queued` (or the stored result of the same key). The owner applies them with `synthesis_orchestrator::apply_queued`: first the decision driver (expiry and invalidation win over a late answer), then each command by CAS: a decision already answered is `already_resolved`, an expired or invalidated one is `stale`, a moved binding or older revision is `stale`, anything the store refuses is `denied`. The kinds this build does not apply (`start`, `pause`, `resume`, `cancel`, `ack`) stay `queued`: fail closed, nothing happens until PR-12's process applies them. While `synt.orchestrator.enabled` is false only `orchestrator.status` answers; nothing is opened or created.
- **Client.** `Stdio` refuses a hello of another version or protocol, and treats as hostile (the connection is dead for every later call): a result nobody asked for, a message that is not a result (`restarted`, asks, ...), a result with neither or both of `ok`/`error`, too many unreadable lines. Replies to mutating calls must echo the key and kind sent; event pages must rise from the cursor. `OutcomeClient::resolve` sends the revision and hash of the card the person was shown and refuses (before sending) a choice the card does not offer or a decision that is not `pending`. `InProc` exists only with the `inproc-test` feature (or `cfg(test)`), and that feature is a compile error in release builds. Waiting has no timeout in the library: the process that owns the pipes runs the watchdog (desktop `remote.rs` does).
- **View models.** `synthesis-view::outcomes`: `DecisionCard::from_json` refuses a brief with a `selected`/`recommended`/`default`... field; `brief_rows` shows every non-empty field of the brief in the server's order, unknown fields included, alternatives in the server's order; `uncovered(brief, rendered)` is the helper each surface's test runs on its own layout; `Picker` starts with no cursor and is `None` unless the decision is `pending`.
- **Dependency rule.** `crates/synthesis-app/tests/surface_deps.rs` fails if `apps/*`, `synthesis-cli-ui*` or `synthesis-view` list `synthesis-orchestrator` under dependencies or build-dependencies (dev-dependencies, used for test fixtures, are not checked; `apps/cli` has one).
- **Unverified.** The surfaces themselves (PR-13 to PR-15); the Windows named pipe and WSL reach of the future `LocalSocket` transport; `Stdio` against the real engine process beyond the status and refusal path.
- **Residuals (PR-11 review).** `surface` is self-asserted: anything that can write the protocol stream can claim any surface; the approver recorded is therefore not proof of who answered until PR-12's owner authenticates the endpoint (threat T-24, T-25). Brief integrity rests on the engine's integrity: the client echoes `brief_sha256` as received and does not recompute it from the brief text. Event pages are returned as the server sent them; surfaces must sanitize every event text before display (PR-13 to PR-15). `inproc-test` is a compile error in release builds, so `cargo test --release` of `synthesis-app` is expected to fail. `apply_queued` stops on a database or I/O error and refuses any other per-command error with a generic reason. A brief is refused when an alternative has a preselect key or an id equal to a fixed answer (`reject`, `request_evidence`, `edit_scope`).

## Implementation notes (view models for plan, criteria, attempts, evidence, budget)

- `synthesis-view::outcomes::views` (re-exported from `outcomes`): `PlanView` (work items, `requires` edges by key, the server's state and order; `layer` is laid out from the server's edges as presentation only; a cycle gives no layers, a dangling requirement is listed and not followed, a duplicate id or key, a bad id or more than 1000 rows refuses the reply), `CriteriaView` (the contract's criteria and checks, no status), `AttemptView` (state as sent; sandbox backend and guarantee are `unknown` when `attempt.inspect` sends no `sandbox` object, i.e. for attempts launched before DDL revision 1009), `EvidenceView` (`event_backed` is the store's boolean from `evidence.get`, `unknown` if absent; result and flags as recorded), `BudgetView` (spent, limit and remaining per tokens, cost and wall time, each `None` unless given, and `reserved_usd` apart; `remaining` is never `limit - spent`), and `InspectorContent` (one variant per tab plus `Unavailable { tab, reason }`; the Diff tab is `InspectorContent::diff_from(attempt.diff reply)` or `Unavailable` with `DIFF_UNAVAILABLE`). Every string is `sanitize_for_display`ed and capped at 4096 characters; ids pass the `valid_alt_id` rule; unknown fields are kept as visible rows; each model has `render_text()` and `uncovered` (the existing helper) proves it shows every non-empty field. No dependency on `synthesis-orchestrator`.
- **Bounds (security review of the view models).** At most 1000 rows per list, 10000 requirement edges per plan and 256 bytes per key (refused beyond); unknown requirements are listed up to 1000 with a count of the rest; layers use Kahn's algorithm (linear) and an item with a requirement outside the plan has layer `unknown`; unknown fields are shown as `server extra: <key>` rows (at most 100 per object, 4096 characters each, a key like `recommended` flagged and ignored, never given a known heading); the sandbox of an attempt is marked server-reported and not verified by the surface, a non-object one is `unreadable`; a `remaining` that does not match limit and spent is shown as the server sent it and marked.
- **Read additions (protocol stays 4; additive, read-only, refused while `synt.orchestrator.enabled` is false, served by the stdio engine and the owner endpoint through the same `Service::handle`):**
  - `outcome.budget {id}` -> `{cost_usd{spent,limit}, wall_secs{spent}, reserved_usd}`. `spent` is what the attempts' sessions recorded (`sessions.usage`); `limit` is the current contract's `max_cost_usd`; `reserved_usd` is the caps of attempts with no final usage yet (the store's `outcome_spend` rule), reported apart because a reservation is a cap, not a spend. `remaining` is not sent (a guess while reservations are outstanding) and there are no token counts (the store does not record any); the wall limit is per attempt, so none is sent for the outcome.
  - `evidence.get` rows carry `event_backed` (the store's own check that the control session has the chained `evidence.recorded` event with the same content). It is necessary, not sufficient: the MAC is the other half, so a surface shows it as "event-backed", never as "verified".
  - `attempt.diff {outcome,id}` -> `{attempt, base_commit, commit, total_files, truncated, files[{path,status,binary,secret,added,removed,patch,patch_truncated}]}`: the attempt's `subject_commit` against the outcome's `base_commit`, repository root, base and commit all from the store (never from the worker, the model or the caller). Produced by `gitsafe::commit_diff` (scratch bare repository, no config, hooks, attributes, filters, external diff or textconv). Caps: 200 files, 16 KiB of patch per file, 128 KiB in all; a binary file has counts only; a secret-shaped path (`synthesis_core::secrets::is_secret_shaped`) has its name only; control characters in paths and patches become U+FFFD; the view model cleans them again and caps a patch at 256 KiB.
- **Sandbox of an attempt (DDL revision 1009).** The owner records, at launch, the sandbox backend name and the filesystem guarantee (`none`/`weak`/`strong`) it resolved itself (`synthesis_sandbox::detect()`, the resolution the enforcing worker also uses) in `attempts.sandbox_backend`/`sandbox_guarantee` (set once, trigger `attempts_sandbox_once`; never reported by the worker). `attempt.inspect` and `item.inspect` send them as `sandbox{backend,guarantee}`, omitted for an attempt without them. Like `bound_policy_hash` the columns carry no MAC (see `docs/specs/session-store.md`): a same-user writer outside the sandbox can rewrite them, so surfaces keep showing them as server-reported, not verified. They say what the owner resolved at launch, not that the worker was enforced or confined by it, and prove nothing about the worker's process. `synt outcome inspect` still prints the raw replies; moving it onto these models is left to the surface PRs (the `--json` schema stays 1 and the raw replies already carry the additive fields).
- **CLI lows closed here:** `synt outcome` reads its `--file` inputs with `O_NOFOLLOW|O_NONBLOCK` and checks `is_file` on the open handle; a decision id, brief hash or outcome id from the server that is not its real shape (`A-Za-z0-9_.-` up to 64; 64 lowercase hex for hashes) refuses the card or row instead of being printed in a command to paste; a brief that offers one answer id twice is refused; `outcome_client::create` keeps its key after a failed link and reuses it on the retry; the owner's `run/orch.log` is opened with `O_NOFOLLOW` and `fchmod` on the handle.

## Implementation notes (PR-12: endpoint, owner-only writes, lifecycle)

- **Who can write.** Mutating methods are accepted only on the orchestrator endpoint. A client proves `run/orch.key` in the mutual HMAC handshake of peers (the key never crosses the wire; nothing but nonces is sent before it is proven), then sends `{"t":"attach","surface":"cli|tui|superagent"}`; the server answers `hello` (exact version and protocol) and from then on refuses any mutating call whose `surface` differs from the attached one. `synt engine --stdio` serves reads only (`Service::read_only`): `decision.resolve`, `outcome.contract.approve`, `outcome.start|pause|resume|cancel|ack`, `outcome.create` and `orchestrator.enable` are refused there, before the store is touched. An agent shell running `synt engine --stdio` therefore cannot answer a decision. This closes the PR-11 residual that `surface` was self-asserted on the stdio link; on the endpoint it is the surface the key-holding process declared, not proof of a person (below).
- **Boundary, stated plainly.** The key is a file of the user. Any program of the same OS user outside the sandbox can read it and attach as any surface; the sandbox keeps attempts away (`run/` is on the deny list: seatbelt test extended, `state_files_protected` extended). So the endpoint is an ownership and correctness boundary, not a security boundary, and the approver recorded (`user:cli`) means "a process that holds the key said so". Person-present signatures are a post-MVP owner decision (ADR-017).
- **Added methods** (served by the owner process only; the stdio engine and `InProc` refuse them): `outcome.create {workspace, base_commit, contract, surface}` (an absolute directory and a full lowercase commit id; the contract is validated by the store and waits in `contract_pending` for `outcome.contract.approve`; PR-12b: an optional `idempotency_key` makes a retry after a lost reply return the same draft (the same key with another request is refused; the record is in the owner's memory), and `base_commit` must exist in the repository) and `orchestrator.enable {surface}` (migration to schema v5 with the store's automatic `backups/pre-v5-*` copy; it does not write settings, `synt.orchestrator.enabled` must already be true). `OutcomeClient::create` and `::enable` are the typed calls. The endpoint serves outcome methods only.
- **Transport.** `LocalSocket` (blocking client over a current-thread runtime), up to 16 connections, requests are strict (an unreadable request ends the link), results must echo the request id (anything else poisons the client link). `Stdio` is unchanged.
- **Notifications.** `notify::outcome_payload` (`{event, outcome_id, decision_id?, kind?, reason_code, ts}`, ids and codes only) for `decision.created`, `outcome.blocked`, `outcome.verified`, deduped in memory per `(decision, revision)` / `(outcome, state, revision)` and sent through `Notifier::start_for_outcomes`: the same confined command (enforcing sandbox, scrubbed env, caps) with the process's own empty working directory. No notify command or no enforcing sandbox means no notification (said once in `run/orch.log`).
- **Not done:** forwarding mutating calls through the stdio engine for WSL surfaces. (The push line, `critical` and durable notification dedupe are settled in the B1/B2 notes below.)

## Implementation notes (PR-13: CLI surface)

- `synt outcome ...` is `synthesis_app::outcome_cmd`: argument parsing, one client call per command, rendering. It does not depend on `synthesis-orchestrator` (the dependency test stays green) and computes nothing: states, needs-you, evidence results and decision states are printed as the server sent them, control characters made visible. A brief is printed whole by the shared `DecisionCard` rows plus the revision and brief hash to quote, and the answers numbered in the brief's order with no marker.
- Answering: `resolve` sends `choice`, `expected_revision` and `brief_sha256` of the card it just fetched, and only after the person supplied the same revision and hash (flags) or picked a number on a terminal. No choice, no send. A stale card prints the new card and exits 2.
- `--json`: one object per call with `"schema": 1`. `status` has `outcome`, `contract`, `plan_version`, `work_items`, `evidence`, `decisions` (cards with `rows` and `options`); the keys are asserted by a test, a change is a schema bump.
- Limits: see the PR-13 status in the plan. The CLI never writes `synt.orchestrator.enabled`.
- Boundary (review): `resolve` is stale-safe (revision and brief hash must match the card) but not presence-safe. The flag path is scriptable and `user:cli` means "a key holder said so": any non-sandboxed process of the user can approve, start or answer a decision (see "Boundary, stated plainly" above; person-present signatures are post-MVP, ADR-017). An answer id is refused unless it is 1 to 64 of `A-Za-z0-9_.-` (it is printed and sent as is, so it is never cleaned). On native Windows every mutating command refuses with the WSL2 text. `--json` failures are exit code plus stderr, not a JSON object.

## Implementation notes (B1 + B2: enable disclosure, decision push, durable notifications)

Design: `docs/specs/orchestrator-remaining-backend.md` (O11, O12, O13). Everything stays behind `synt.orchestrator.enabled`.

- **Enable disclosure (B1).** `synthesis_app::outcome_policy::INTEGRITY_DISCLOSURE` is the plan 3b item 6 text plus one sentence: there is no person-present signature yet, so a program running as the user outside the sandbox can read the key and forge an approval, an event or evidence. The owner's `orchestrator.enable` reply carries `disclosure: {id: "integrity-v1", text}`; `OutcomeClient::enable` refuses a reply without it (fail closed) and the CLI prints the server's text after enabling, and its own `ENABLE_NOTICE` (same first paragraph, locked by a test and by a test against the plan) before `--yes`. A surface renders the text and never words it. The id changes when the text does.
- **Push (B2).** `attach` takes an optional `"push": ["decision"]` (anything else, or a non-array, ends the link as a bad attach). `PROTOCOL` stays 4: a link that did not opt in never receives one, so the hostile-engine rule is unchanged, and `DecisionHint` is not an `Out` variant, so a stdio engine that sends it is still poisoned. The line is `{"msg":"decision","outcome","id","revision","state"}`: ids, a revision number and a state word, never brief text. The owner publishes after each cycle for every decision that is new or whose `(revision, state)` changed since the last look (what exists when an outcome is adopted is not published). The endpoint keeps one broadcast queue of 64 per push link; a slower reader loses the oldest hints and keeps the newest. A hint is a wake-up only: `LocalSocket` accepts it only when it opted in and only in the strict shape (five keys, `valid_alt_id` ids, a known state), queues up to 64 that arrive while it waits for a result, and `OutcomeClient::next_hint` hands them out; the surface refetches with `decision.list` and renders the server's answer, so a forged state in a line shows nothing. Hints do not extend the idle timeout of a link (requests do).
- **No new notify kinds.** `decision.created` (kind is in the payload), `outcome.blocked`, `outcome.verified` as before.
- **`critical` removed.** Nothing ever defined or populated it: the server's `needs_you` and the CLI's `--json` (still `"schema": 1`) had only `decisions_pending`, `blocked`, `verified_awaiting_ack`; removing the name from this ADR changes no output. A "critical" badge would invite hurried approval (T-09); if it is wanted later it must be derived by the store from the stored action, never by a surface.
- **Durable dedupe.** Before a notice is handed to the hook the owner writes an `outbox` row (`kind` `notify`, key `notify:<event>:<id>:<revision>`, payload without text or time) and marks it `done` in the same call; only the call that created the row sends. A restart (empty in-memory set) finds the row and stays silent; a crash after the mark and before the hook ran loses that one notice, never repeats it (at-most-once; `needs_you` is derived from rows, so the decision still shows). No schema change (`outbox.kind` is free text; an older build parks a `notify` row as an unknown kind). The in-memory set and the notifier caps stay.
- **CLI.** `synt outcome decisions ID --watch` attaches with push, prints the cards, then reprints a card only when its `(revision, state)` changed, refetching on a hint for that outcome or after 60 s without one (this also keeps the link open and covers a dropped hint). It ends when the link closes.
- **Not done:** a resync marker for a link that lagged (the client refetches on its own timer instead); push through the stdio engine; surfaces other than the CLI (TUI and Super Agent use `LocalSocket::connect_with(.., true)` and `OutcomeClient::next_hint`); Windows named pipe push is untested (the endpoint tests are unix-only).

## Implementation notes (B3: re-brief, enable disclosure check)

- **No protocol change** (`PROTOCOL` stays 4). A re-brief is a normal new decision: `decision.list` returns the old card (`invalidated`) and the new one (`pending`) whose brief has `supersedes`, `rebrief`, `rebriefs_left` and `evidence_summary`. Surfaces render every brief field already (field-coverage test), so the link is shown as a row `supersedes: <old id>`; no surface computes it. The `decision.resolve` result for `request_evidence` and `edit_scope` carries a `note` (plain text from the owner).
- **Client:** `OutcomeClient::enable` compares the owner's `disclosure.id` and `disclosure.text` with this build's `DISCLOSURE_ID` and `INTEGRITY_DISCLOSURE` and refuses any difference (an owner of another build). Test `a_changed_disclosure_text_needs_a_new_disclosure_id` pins the id with the hash of the text, so changing the text fails until the id is bumped.
- Golden: `a_rebriefed_card_shows_its_supersedes_link_and_the_old_card_cannot_be_answered` (`outcome_cmd` tests); e2e through the real owner: `request_evidence_gets_a_new_card_that_names_the_old_one_and_only_it_can_be_answered` (`apps/cli/tests/outcome_e2e.rs`).

## Implementation notes (B5: gateway at the endpoint)

- **No protocol change** (`PROTOCOL` stays 4). The principal of a call is the surface the link attached as (or `engine` for the stdio server), never a param: a mutating call that names another surface is refused as before, and the gateway table (ADR-019 B5 notes) then decides. Every mutating `Call` variant maps to a gateway action (`Call::action()`, exhaustive; test `every_mutating_call_maps_to_a_gateway_action_named_like_its_method`). Allowed and finished commands are audited in the control session; link-level denials are a stderr line of codes. Not a security boundary against a same-user process holding `run/orch.key`.
