# Unattended runs

Status: implemented on branches `feat/harness-governance` and `feat/governance-leftovers`; owner decisions below were delegated with safe defaults and are to be reviewed. Terms: CLI = the terminal app, TUI = the desktop tab.

`synt run` (headless) and `synt engine --stdio` are treated as runs nobody watches. The interactive CLI and the desktop's in-process sessions are unchanged unless you set a limit yourself.

## Defaults of `synt run` and `synt engine --stdio`

| What | Default | Opt out |
|---|---|---|
| Wall clock | 1800 s per task | `--max-wall-secs N` |
| Cost cap | REQUIRED: the run is refused (exit 2) without one | `--max-cost-usd X`, or `--no-cost-cap` |
| Tokens | no cap | `--max-tokens N` (input + output + cache tokens) |
| Worktree | used when the directory is a git repository with a commit; it starts from the tree as it is (uncommitted and untracked work included, detached HEAD works, submodules are NOT checked out unless `synt.worktree.submodules` is true, see below; a notice lists them). A notice names the worktree path and branch. If it cannot be made, a plain headless run falls back to the directory with a loud warning; `--unattended` refuses | `--no-worktree` |
| Inferred-only checks | a task whose only checks were inferred stays `unverified` (exit 3) | an explicit `"inferred_only": "allow_passed"` in your settings |
| Session store | a message that cannot be stored ends the task `failed` (`context_error: session_store: ...`) | `--no-session-store` |
| Sandbox | enforce. Native Windows has no confinement: the run is refused unless `--sandbox off` is explicit | `--sandbox off` (loud warning) |

`synt engine --stdio` takes `--max-cost-usd`, `--no-cost-cap`, `--max-wall-secs`, `--max-tokens` and the common flags. A desktop host launches it with `--host desktop`: a person is at the window, so there is no default worktree, no default wall cap and no required cap; the interactive store behaviour applies. The desktop passes the cap itself (below).

### Desktop (WSL) cost cap

The Windows desktop runs `synt engine --stdio --host desktop --max-cost-usd N` in WSL. `N` is `synt.desktop.max_cost_usd` (user or managed settings, managed wins; default 10 USD per task). `synt.desktop.no_cost_cap: true` is the explicit way to run without one (the flag is then not passed). The cap needs a price for the model: built in for Anthropic and OpenAI models, otherwise `synt.pricing` inside WSL, or the session does not start and says so.

## `--unattended`

One flag for all of the above, stricter: worktree is mandatory, the cost cap cannot be waived, inferred-only is forced to `cap_unverified` even if your settings say `allow_passed`, network must be `deny` or `hosts` (`--network hosts`: only the hosts of `synt.sandbox.network.allowedHosts` in your user or managed settings, through the egress proxy; `--allow-host` is refused here; docs/specs/sandbox-hardening.md), peers are off, the session store cannot be disabled. It REFUSES to start (exit 2) if the sandbox is not enforceable here, the directory is not a git repository with a commit, a resumed session had no worktree, or one of `--sandbox off|best-effort`, `--network allow|loopback`, `--permission-mode bypassPermissions`, `--trust-project`, `--approve-mcp`, `--no-worktree`, `--no-session-store`, `--peers`, `--no-cost-cap` is given. Out of scope (still allowed): `--allow` rules (an allow rule for an irreversible command is yours to judge), MCP servers and hooks from your own user settings, `--add-dir`, `--sandbox-read`, and anything the model does inside the sandbox and the worktree (a pushed branch, a network-less but destructive command).

## Verification gate and unattended runs

The gate (docs/specs/verification.md) freezes the checks at the task start, keeps a baseline file (`gate-baseline.json` under the session's artifact dir, no database change), and caps a pass at `unverified` for planned test checks that did not pass, changed definitions, modified test files and model-declared checks. On top of that, a headless run or engine treats `inferred_only` as `cap_unverified`: with no user criteria, inferred checks alone end the task `unverified` (exit 3) even when they passed, which main's gate would otherwise accept as `passed`. The unattended default is stricter than the gate default; your own `"inferred_only": "allow_passed"` in the USER settings lifts it for a plain headless run (never under `--unattended`). Every `unverified` outcome of the gate keeps exit 3.

## Cost accounting

Every response is priced on input, output, cache read and cache creation tokens. Also charged to the task counters (and so to the cap): the summarizer calls of compaction, the auto-mode judge's calls (at the judge model's price, cache tokens included) and, in a headless run, the memory reflection that runs after the task (its USD is added to the session's stored usage; in the desktop and the CLI the reflection runs in the background and its cost is only in `memory.reflection.completed` and the daily reflection budget). Prices: `synt.pricing` of the user settings, else a built-in table for first-party models (approximate; the dearer price of a family so a cap does not under-count). See docs/specs/config.md section 6.

**Pre-turn estimate.** Before each model call under a cost cap the harness computes the worst case of that call: `prompt x P_in + max_output x P_out`, where `prompt` is the estimated request (the calibrated estimator; 20% margin until the provider has reported a size), `P_in` is the dearer of the input and cache-write prices (long-context tier included) and `max_output` is the request's `max_tokens`. What is available is `cap - spend - the worst cases of calls still in flight` (each call RESERVES its worst case in the task counters until its response is accounted, so parallel sub-agents cannot all spend the same remainder). If the worst case does not fit, `max_tokens` is LOWERED to what the remainder affords (a notice says so once); only when even `min(max_tokens, 4096)` does not fit is the call refused. A refused call stops the task with `budget.exceeded` (`budget: "max_cost_usd_estimate"`, `limit` = the cap, `used` = the ACTUAL spend so far, `estimate: true`, `estimate_usd` = the worst case of the refused call) and the task ends `budget_exceeded:max_cost_usd_estimate` after the usual final evaluation (never `completed` without a passing report). UIs show it as "stopped before the next call: it could cost up to $X". The estimate is conservative on purpose: a response almost never uses all of its output limit and the cache makes input cheaper, so a task can stop with money left. Minimum usable cap: about one call with a 12000 token prompt and 4096 output tokens at the model's price (`synt run` warns below that and refuses below the price of 4096 output tokens alone; Opus-class prices of 15/75 USD per million need about 0.5 USD, so a 1 USD cap works with a clamped output limit, which can truncate long answers). Lowering `max_tokens` below a model's thinking budget is not handled. A response that is actually cut at its output limit is always said so in a warn notice; a FINAL answer that was cut ends with the marker `[answer cut at the output limit]` instead of passing as a complete report; and three batches in a row of only cut-off tool calls under a lowered limit end the task `budget_exceeded:max_tokens_clamp` (the limit is too small for this cap: raise the cap). Built-in prices are approximate and conservative: `claude-opus-4-5` is listed at the Opus 4/4.1 price (15/75), which is probably higher than the vendor's current one; nothing in the repo confirms either, so the dearer is kept. The check after each response stays (`max_cost_usd`). A model that has no price never borrows the run's: under a cap the call is refused (`budget_exceeded:max_cost_usd_unpriced`), and a capped run is refused at start when a fallback or a sub-agent model has no price or cannot be resolved. Each response is priced by the model that answered it: the run's model, a sub-agent's model or a failover target; under a cap every fallback and sub-agent model must have a price or the run is refused at start. Built-in prices match exact ids (and a date suffix) only: `gpt-5-pro`, `o3-pro`, `o4-mini-deep-research` and newer Claude ids have no built-in price, so a capped run is refused until `synt.pricing` prices them.

**Long-context tiers.** A request whose prompt (input + cache tokens) is above a threshold is priced as a whole at multiplied rates (`LongTier`: `input_mult` on every input-side price, `output_mult` on output). A `synt.pricing` row with a non-numeric, negative or non-finite price, or a multiplier below 1, is IGNORED as a whole with a stderr warning naming the key (never the value). Built in: Sonnet 4 and 4.5 (the models with a 1M context) and the `gpt-5*` and `gpt-4.1*` families, above 200k tokens, 2x input and 1.5x output. These are conservative approximations where a vendor's tier is not certain (the dearer reading wins); a model with a context shorter than 200k has none. Override or remove in a `synt.pricing` row with `long_above_tokens`, `long_input_mult`, `long_output_mult` (omitted multipliers are 1; set `long_above_tokens` very high to switch a built-in tier off); a row without `long_above_tokens` keeps the model's built-in tier. The pre-turn estimate applies the tier too.

**Cached tokens.** OpenAI-compatible providers report cached tokens INSIDE `prompt_tokens`; the provider adapter now subtracts them, so `input_tokens` excludes cache tokens for every provider and a cached token is priced once, at the cache-read price (built-in OpenAI rows: 10% of input for `gpt-5*`, the dearer 50% for the other models). Events and stored usage of OpenAI-compatible sessions therefore show a smaller `input_tokens` than before and the cache tokens separately. Gateways report this differently at times; a gateway that already excludes them is counted as given.

## Stopping a run

`synt stop SESSION` from any terminal sets a stop request in the session store. It works only on a session that a live process holds (`synt run`, `synt engine --stdio`, the CLI); for anything else it prints "no live process holds this session" and exits 1, never 0. The process polls once a second, cancels the task (graceful, exit 130 / `cancelled`), and after 15 s kills the process groups of its commands, marks the row `interrupted` (best effort, bounded to 3 s) and exits 130. Only a request made after the process started counts, so an old request does not stop a resumed session, and a request made while a resume is still preparing is not lost. If the stop flag cannot be read five times in a row the session is stopped anyway (fail closed) and stderr says why. The second Ctrl-C / SIGTERM of `synt run` runs the same bounded kill (on macOS and Linux commands live in their own process groups, so a bare `exit` used to orphan them). Needs the same `SYNT_HOME`. A desktop window's in-process session (`synt stop` finds it through the store lock, like any holder) is stopped WITHOUT exiting the app: its watcher cancels the session (not just the running task: the session is over and a new one is started from the window), tells the window through a callback (a note in the chat), and after the same 15 s kills the commands' process groups and marks the row `interrupted`. The holder writes `sessions/<id>/stop-mode` (`process` or `in-process`) and `synt stop` prints which mechanism acts ("mechanism: process exit" or "mechanism: in-process; the app that holds this session stays open"). A process that cannot be reached still prints "no live process holds this session" and exits 1. `synt stop` on a desktop in-process session also CLOSES its engine in the window (hooks, store, runtime), so the stopped session is gone, not half alive. The hard exit of the interactive CLI (and the second Ctrl-C of any run) restores the terminal first (cooked mode, main screen, cursor), because `process::exit` runs no destructors; the restore runs on a helper thread and is waited for at most 500 ms (a stuck writer or a stopped terminal cannot keep the process alive; raw mode is then switched off directly); covered by a pty test and a stuck-writer test. The watcher stops when the session ends (`Live::close`), so a late `synt stop` of an ended session does nothing and no watcher outlives its session.

## Audit trail

Each stored event carries `prev`, an HMAC-SHA256 (key: the per-user file `$SYNT_HOME/chain.key`, 0600, outside the database) over the previous link and the event row; the session row keeps the head and a `chained` flag set at creation. `synt sessions verify ID` recomputes it: exit 0 verified, 1 TAMPERED (an event changed, removed, cut off at the end, a link or the head removed on a chained session), 3 NOT VERIFIED (a session created before the chain existed, or the key file is gone). SCOPE: the `events` table only. Tasks, verification reports, approvals, messages and tool_calls are NOT chained; `verification.completed` carries the sha256 of the full report so the stored report can be compared with the event. Streaming `model.delta` bodies are not covered (they are compacted in place; the final `assistant.message` is). Event payloads moved to artifacts are covered by their artifact id, not their bytes. LIMIT: tamper evidence, not prevention. Someone who can write only `synt.db` cannot forge the chain; a process of the same user outside the sandbox can read the key and rewrite everything. The sandbox denies `$SYNT_HOME` to the agent's commands.

`synt sessions show ID [--events] [--report]` prints the timeline, budget use, the active model (after a failover) and the stored verification reports (redacted again, control characters made harmless). The report row now holds the full report as `synthesis-verification` serialises it; older rows hold the one-line summary.

## Resume of a worktree session

The worktree's pins (`GitInfo`) are stored in the session row. `--resume ID` re-pins them only if the record names one of this tool's worktrees (`$SYNT_HOME/worktrees/<session id>` of the recorded repository, git pointers matching) and continues in it; otherwise or if it is gone it refuses. `--resume` / `--continue` find a session that ran exactly in this directory or in the worktree this exact directory got (the repository top, or the same subfolder). `--fork-session` starts a new session in a new worktree.

## Provider failover

`"fallback": ["provider/model", ...]` in the user `config.json` (docs/specs/config.md). Only before the first byte and only for rate limit, overload and server errors; emits `model.failover`. The switch holds for `fallbackReprobeMinutes` (default 5), then the primary is asked again and a `model.failover` event with reason `primary_recovered` says when it answers. `synt sessions show` names the active model. DATA EGRESS: a failover sends the conversation (prompts, file contents the model read, tool output) to the fallback provider, under that provider's data policy and key; only list providers you accept for the same work. A fallback that cannot be built stops an unattended run and is warned about in the CLI.

## Worktree submodules

`git worktree add` leaves submodules empty. With the USER or MANAGED setting `synt.worktree.submodules: true` (default false; a project file can never turn it on, its `.gitmodules` is untrusted) the implicit worktree checks them out through the hardened git wrapper (no global config, no hooks, `protocol.allow=never` with only `https` and `ssh` re-enabled, `core.sshCommand=ssh -o BatchMode=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=2`, git's low-speed limits, `submodule.<name>.update=checkout` pinned for every name). Needs a git with the submodule security fixes (CVE-2024-32002, CVE-2025-48384): 2.50.1 or later, or 2.49.1, 2.48.2, 2.47.3, 2.46.4, 2.45.4, 2.44.4, 2.43.7 (else refused with the version found and, for macOS, the hint to `brew install git`; Apple's git is usually older than the floor, and its number is judged like any other). `synt.worktree.gitPath` in the USER or MANAGED settings (an absolute path; never a project file) points the worktree code at another git, e.g. `/opt/homebrew/bin/git`, whose version is checked the same way. `GIT_CONFIG_GLOBAL` needs 2.32, covered by that floor. It runs level by level (`git submodule update --init`, not `--recursive`) so the URL policy also runs on the `.gitmodules` of every submodule BEFORE it is cloned: at most 50 submodules over at most 3 levels, one 5 minute deadline for everything (the git process group is killed after it; a git that exits while a helper still holds its pipes is an explicit error, never cut output taken as success; on Windows `taskkill /T /F` ends the tree, and output readers are detached after 2 s so an escaped helper cannot hang the call). No repository lock is held during the clone, and nothing is written to the shared `.git/config`: URLs and `active` are passed with `-c`, git puts the clones under the worktree's own git directory. A URL must be `https://`, `ssh://` or scp-like `[user@]host:path` with a plain host (never starting with `-`; IPv6 literals and anything containing `::` are refused), no credentials (`https` with any userinfo, `ssh` with a password), no literal internal host (loopback, private, link-local, carrier-grade NAT, multicast, `localhost`, `*.local`, `*.internal`, a trailing dot ignored, dotted numeric or `0x` forms like `2130706433` or `0x7f.1`; ordinary names such as `git0x.io` pass); a NAME that resolves to an internal address is NOT detected (no DNS lookup): use the network policy, and `ssh` with at most a plain user name. `file:`, `ext::`, `git://`, `http://`, relative paths, option-like values (`-o...`, `ssh://-oProxyCommand=...`, `u@-oFoo:p`), control characters (CR, LF, TAB, NUL) in URLs, names and paths, a path that leaves its directory, an `update = !command` entry and a symlinked `.gitmodules` refuse that level (what an earlier level cloned stays) and the notice says which. Messages and notices never print credentials of a URL (userinfo is stripped; git's own error text is reduced to its first line and scrubbed). With the setting off (the default) the run starts and a notice lists the submodules and shows the setting. The `file` transport exists only in the unit tests of `synthesis-workspace` (an injectable policy compiled under `cfg(test)`). Resumed worktree sessions are not re-populated. Git credentials for private submodules are not provided (the git environment is the allowlisted one; `ssh` needs an agent socket that is not passed), so private submodules need your own setup. On Windows only the git process is killed at the deadline, not its children.

HOST-SIDE GIT NEVER DESCENDS INTO A SUBMODULE. A checked-out submodule's `.git` file is writable by the agent and could point at a git directory with a filter or similar in its config; the host's own `git add`/`diff`/`status` would run it unsandboxed. The hardened git wrapper therefore sets `diff.ignoreSubmodules=all`, `status.submoduleSummary=false` and `--ignore-submodules=all` on every diff, and `add` excludes every gitlink path. Consequence: changes made INSIDE a submodule do not show up in `changes`, `diff` or the host's commit of the worktree. A test plants such a filter and checks it never runs.

## Notifications

Optional, for governed runs (`synt run`, `synt engine --stdio`; never the interactive CLI). Setting in the USER or MANAGED settings (managed replaces user; a project file is never read):

```json
{"synt": {"notify": {"command": ["/usr/local/bin/my-notify", "--chan", "ops"], "timeout_secs": 10, "network": false, "include_text": false}}}
```

`command` is an argv array (1-64 elements, each non-empty), not a shell string: the runtime hands it to the shell as single-quoted words, so nothing in it is expanded. It gets ONE JSON event on stdin and runs through the sandboxed terminal runtime (the run's sandbox policy, the workspace as cwd) in its own runtime session with a scrubbed env (PATH, HOME, locale, temp dir only: no API key, no `SYNT_*`, no `settings.env`) and a timeout of `timeout_secs` (1-60, default 10) after which it is killed. It is NOT started when the run is not sandboxed (`--sandbox off`, best-effort, or a policy that could not be built): a notifier must never run unconfined for a run that asked for confinement; a notice says so. `network: true` lets it reach the network (a webhook), but under `--network hosts` the notifier keeps the run's proxy (its host must be allowed); the default is the run's own network policy, which is `deny` under `--unattended`. At most 4 commands run at once (the rest wait), at most 50 notifications per process plus a separate allowance of 50 for `task.ended`, so approvals cannot crowd the final event out; a failure (command, thread or runtime) is one stderr line and never changes the task result. Events: `task.ended` (any status: `{"event","session_id","task_id","ts","status","reason_code","cost_usd"}`), `approval.blocked` (a headless run denied an ask because nobody can approve; once per task; `reason_code: "approval_unavailable"`) and `budget.exceeded` (`budget`, `limit`, `used` = actual spend, `estimate`, `estimate_usd`). `reason_code` is one of `budget_exceeded`, `cancelled`, `no_progress`, `model_error`, `context_error`, `verified`, `unverified`, `approval_unavailable`, `internal`, `other`; the redacted stop reason text (cut to 200 characters) is added as `reason` only with `"include_text": true`. `synt run` waits for running notifications before it exits, at most 10 s in total; a session of the engine or the desktop does so when it is closed (`Live::close`), which also closes the notifier's runtime session.

Threat model. The payload is built from the event stream after redaction and holds only ids, the status, a reason code and budget numbers: never the final answer, the request, tool input or output, file names or contents (and by default no free text at all). The command is chosen by you; the model and the repository cannot set or change it. The command is a program you run with the sandbox's limits; what it does with the payload (a webhook) is outside this tool. NOT covered: a run killed by `synt stop`'s hard exit or SIGKILL sends nothing after the kill; `kind: "desktop"` (a system notification from the desktop app) is accepted but skipped with a notice, because the app has no notifier today; the interactive CLI does not notify. Not supported on native Windows without Git Bash (the notifier needs the POSIX shell).

## Not fixed / residual risks

- Notifications: see above for what is not covered; the desktop notification kind is a stub.
- The session-store failure ends the task as `context_error: session_store: ...`, not a bare `session_store` reason.
- The hash chain is tamper evidence only and covers events only (see above). Artifact bytes are not chained.
- Failover keeps the primary's context window and output limit; a smaller fallback can fail with context overflow.
- Windows: the Job Object cannot confine, so a headless run does not start unless `--sandbox off` is explicit (the refusal says `--sandbox off (explicit, unconfined)`; best-effort is never offered to an unattended run). Unverified on a real Windows machine; the logic is unit-tested only. WSL2 is the supported route for autonomous runs; native confinement (AppContainer) needs an owner-approved ADR-010 exception.
- The pre-turn estimate is an upper bound of the call, not of the task, and uses the estimator (a few percent off, calibrated against the provider's own count after the first response); a provider that does not honour `max_tokens` can still overshoot.
- Tier thresholds and multipliers are approximations; a vendor's price change is not followed until the table is updated.
- `--network hosts` limits destinations only: an allowed host that accepts uploads can still receive anything the commands can read. Under `--unattended`, `readScope: host` is forbidden (decision of the owner; not built yet) and missing cgroup limits only produce a notice.
- A wall cap bounds a task, not a long-lived engine session of many tasks.
