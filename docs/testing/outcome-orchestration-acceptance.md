# Outcome orchestration: acceptance tests

Status: Proposed (2026-11-14, rev 2: protocol-level acceptance for three surfaces). Every acceptance criterion AC-01..15 and every adversarial scenario of the design (sections 28 and the security list) is specified here as an executable test. Related: [gap analysis](../architecture/outcome-orchestration-gap-analysis.md) (current state), [threat model](../architecture/outcome-orchestration-threat-model.md) (ids T-xx), [plan](../architecture/outcome-orchestration-plan.md) (the PR that delivers each test), [MVP slice](../architecture/outcome-orchestration-mvp-slice.md).

## 1. Conventions

- **Harness kinds.** `unit` = Rust test inside the crate; `crate` = `crates/<c>/tests/<file>.rs`; `proto` = **protocol-level headless test**, `crates/synthesis-app/tests/outcome_proto.rs`, driving the orchestrator through the same client library every surface uses (`synthesis_app::outcome_client`; transport `InProc` for most cases and `LocalSocket` for process-lifetime cases) with the scripted fake model (cargo feature `test-provider`, as `apps/cli/tests/e2e.rs` does); `surface` = a thin per-surface test of rendering and command dispatch only (section 5); `redteam` = a case in `tests/redteam/cases.mjs` (the suite plays one `synt run` attempt per case in four modes; it cannot drive `synt outcome`, so only single-attempt attacks live there); `eval` = `tests/agent-evals`. New file or case names are **proposed**.
- **Acceptance is protocol-level first** (owner point 14, plan multi-surface rule 14): every AC and security row is proven headless through the protocol. Surfaces get only the thin tests of section 5. No lifecycle behaviour may be tested only through a GUI, a terminal screen scrape or the `synt` binary's text output.
- **Fixture `repo-endpoint`** (new, `tests/fixtures/outcome/repo-endpoint/`): a tiny git repo with a one-function endpoint, a unit test, a deliberately failing test used by AC-07, an `infra/prod/` directory and a `.env`-like sentinel file. Built by the test into a temp dir (no committed `.git`); canonical temp paths (macOS `/var` -> `/private/var`).
- **Scripted model.** The `test-provider` plays fixed turns; where the design says "worker obeys an injection" the script obeys it (same technique as `tests/redteam`).
- **Platforms.** `P3` = macOS, Ubuntu, Windows (`test` job matrix). `PU` = macOS and Ubuntu only (sandbox-dependent; Windows skipped with a stated reason, ADR-018 item 5). `PL` = Ubuntu with bubblewrap (`sandbox-linux` job, `SYNT_REQUIRE_BWRAP=1`).
- **Reuse today** says whether an existing test already covers part of the criterion.
- **Determinism.** No test depends on `TERM`, `COLORTERM`, `$HOME` contents or wall-clock sleeps longer than a bounded poll; time-based behaviour (expiry, lease) uses an injectable clock in `synthesis-orchestrator`.
- A criterion is not done until its tests ran on the platforms listed (CLAUDE.md "Cross-platform is a requirement").

## 3c. Real-worker end to end and the AC-04 kill matrix (implemented, `apps/cli/tests/outcome_e2e.rs`)

Through the real `synt outcome` CLI, the real owner process (`synt orchestrator --serve`, started by the first command) and real workers (`synt run --unattended` in a sandbox) that replay a scripted model. The owner takes the script from `SYNT_TEST_ORCH_SCRIPT` (workers get `--provider fake:<script>`) and an optional pause file `SYNT_TEST_ORCH_HOLD` (no scheduler tick while it exists); both are read only in builds with feature `test-provider` (`TestHooks` in `orch_owner.rs`; a release build with the feature is a `compile_error`, they are not settings). Unix only; a host without an enforcing sandbox skips (fails under `SYNT_REQUIRE_BWRAP`). The scenarios run one at a time (2 to 3 minutes in a debug build). The model's script is shared by every worker of a test (the file can be swapped between attempts); `after_file` holds a worker mid-attempt.

| Test | Covers |
| --- | --- |
| `a_worker_edits_a_worktree_and_an_independent_check_gives_the_verdict` | create, contract, approve, start, worker edits its own worktree (user's repo untouched), frozen check run by the independent runner, `verified`, `ack` to `completed`, no `outcome.recovered` (AC-01 path, AC-06 part) |
| `a_worker_that_says_done_without_the_file_is_not_verified` | the worker's claim is not evidence: the check fails, the outcome blocks, `ack` is refused |
| `a_decision_a_blocked_worker_made_is_answered_only_with_an_explicit_choice` | a real `AskUserQuestion` block becomes a decision; card, no preselection, bad choice and stale revision refused, answer (the blocked outcome runs on by itself, no `resume`), the next attempt finishes, a second answer is not applied (replaces the store-seeded decision where a worker can run) |
| `kill9_after_create_...`, `kill9_after_approve_...` | the contract (approved or not) survives; a new owner serves the same single outcome |
| `kill9_after_start_before_any_worker_spawns_...` | start applied and planned, no worker yet (held): after adoption exactly one attempt per agent item, `start` applied once |
| `kill9_of_the_owner_the_worker_ends_alone_and_the_next_owner_settles_it_once` | AC-04 "after attempt end before evidence": `outcome.recovered` `settled`=1, one attempt, one verdict row |
| `kill9_of_the_owner_with_a_live_worker_the_next_owner_leaves_it_alone` | `outcome.recovered` `alive`=1, the worker is not killed or rerun, the outcome stays `running` (its reservation does not block it), after the worker ends the attempt is settled once and the outcome reaches `verified` with one verdict row |
| `kill9_of_the_owner_and_its_worker_mid_attempt_...` | `outcome.recovered` `lost`=1, the lost attempt is not rerun (no second attempt or worktree), no evidence for it, the outcome stops `blocked` with the cost-cap reason and the real numbers; `resume` blocks it again |
| `kill9_of_the_owner_and_its_worker_with_budget_left_...` | the lost attempt keeps its (small) reservation, the item gets a new attempt in a new session, the outcome reaches `verified` without `resume` |
| `kill9_during_verification_...` | owner killed while the frozen check runs: the check is run again by the next owner, exactly one verdict row |
| `kill9_after_the_verdict_before_the_ack_...` | `verified` stands, adoption writes no evidence, `ack` completes |

Every recovery test also asserts: no queued command left, one `contract_approved`, one applied `outcome.start`, exactly one passing `t` row made by `independent_runner`, on the commit of the finished implement attempt.

**Not covered.** (1) "After worktree create before DB commit" and the outbox sub-case (SEC-08): no fault is injected between those steps; only the process-level kill points above are exercised. (2) A command queued while the owner is down (a client always starts an owner first). (3) Evidence MAC and `synt sessions verify` on the control session after recovery. (4) Linux with bubblewrap, Windows: written for unix, run on macOS only. (5) The `ac04_restart_recovers_without_duplicates` 3-item variant and `perf_recovery_100`.

**Findings of this work, now fixed (recovery follow-up).** (a) A live worker adopted by a new owner (owner killed, worker survives) used to be unpolled and its reservation (the whole cap) blocked the outcome. Now: while an adopted attempt lives, its reservation is its own share and does not block (`kill9_of_the_owner_with_a_live_worker_the_next_owner_leaves_it_alone` asserts the outcome stays `running`); the owner renews its lease (within the worker's own wall cap), and when the worker ended it settles the attempt from the session store (`recover_item` on every tick, so a `resume` also settles) and the outcome goes on to `verified`. (b) After a whole-machine loss the lost attempt keeps counting its whole reservation as spent (its session recorded no final usage); the attempt is `lost`, never rerun in place, never given evidence. With budget left (`kill9_of_the_owner_and_its_worker_with_budget_left_a_new_attempt_does_the_work`: attempt cap 0.5 of 5.0) the work item gets a NEW attempt with a new session and the outcome continues without a `resume`; with none left (`kill9_..._the_lost_attempt_is_not_rerun`: one attempt held the whole cap) the outcome is `blocked` with the numbers ("spent or reserved $5.0000 of $5.0000; an attempt whose worker died without a final usage counts its whole reservation"), and `resume` blocks it again. (c) Answering a decision now moves a `blocked` outcome by itself (`a_decision_a_blocked_worker_made_is_answered_...`, no `resume`); see ADR-019 recovery notes. Unit level: `an_adopted_live_attempt_keeps_its_reservation_without_blocking_and_a_lost_one_is_never_rerun` (`tests/sched.rs`) and `the_ledger_never_exceeds_the_cap_under_any_start_adopt_lose_settle_order` (`tests/runner.rs`, seeded random order of start, adoption, loss and settle: the ledger never exceeds the cap, adoption never changes it).

**Accounting rule (exact).** Per attempt the ledger counts: the session's final usage if the session ended with one (never below what was written), else `max(reservation, usage written so far)`. `lost`, killed, crashed and adopted-alive attempts without a final usage count their whole reservation; a reservation is set once and only lowered. A new worker gets at most `(cap - spent) / share`, so the sum never exceeds the cap. The outcome is blocked for cost only when the cap is used up AND no attempt is alive: a live attempt's reservation is part of `spent` but it is not an overrun, and the live worker will free or fix its reservation when it ends. A residual remains: a sole attempt that held the whole cap and was lost leaves nothing (a person must raise the cap with a new contract version or set `attempt_max_cost_usd` so attempts do not hold the whole cap).
