# Outcome orchestration: acceptance tests

Status: Proposed (2026-11-14, rev 2: protocol-level acceptance for three surfaces). Every acceptance criterion AC-01..15 and every adversarial scenario of the design (sections 28 and the security list) is specified here as an executable test. Related: [gap analysis](../architecture/outcome-orchestration-gap-analysis.md) (current state), [threat model](../architecture/outcome-orchestration-threat-model.md) (ids T-xx), [plan](../architecture/outcome-orchestration-plan.md) (the PR that delivers each test), [MVP slice](../architecture/outcome-orchestration-mvp-slice.md).

## 1. Conventions

- **Harness kinds.** `unit` = Rust test inside the crate; `crate` = `crates/<c>/tests/<file>.rs`; `proto` = **protocol-level headless test**, `crates/synthesis-app/tests/outcome_proto.rs`, driving the orchestrator through the same client library every surface uses (`synthesis_app::outcome_client`; transport `InProc` for most cases and `LocalSocket` for process-lifetime cases) with the scripted fake model (cargo feature `test-provider`, as `apps/cli/tests/e2e.rs` does); `surface` = a thin per-surface test of rendering and command dispatch only (section 5); `redteam` = a case in `tests/redteam/cases.mjs` (the suite plays one `synt run` attempt per case in four modes; it cannot drive `synt outcome`, so only single-attempt attacks live there); `eval` = `tests/agent-evals`. New file or case names are **proposed**.
- **Acceptance is protocol-level first** (owner point 14, plan multi-surface rule 14): every AC and security row is proven headless through the protocol. Surfaces get only the thin tests of section 5. No lifecycle behaviour may be tested only through a GUI, a terminal screen scrape or the `synt` binary's text output.
- **Fixture `repo-endpoint`** (new, `tests/fixtures/outcome/repo-endpoint/`): a tiny git repo with a one-function endpoint, a unit test, a deliberately failing test used by AC-07, an `infra/prod/` directory and a `.env`-like sentinel file. Built by the test into a temp dir (no committed `.git`); canonical temp paths (macOS `/var` -> `/private/var`).
- **Scripted model.** The `test-provider` plays fixed turns; where the design says "worker obeys an injection" the script obeys it (same technique as `tests/redteam`).
- **Platforms.** `P3` = macOS, Ubuntu, Windows (`test` job matrix). `PU` = macOS and Ubuntu only (sandbox-dependent; Windows skipped with a stated reason, ADR-018 item 5). `PL` = Ubuntu with bubblewrap (`sandbox-linux` job, `SYNT_REQUIRE_BWRAP=1`).
- **Reuse today** says whether an existing test already covers part of the criterion.
- **Determinism.** No test depends on `TERM`, `COLORTERM`, `$HOME` contents or wall-clock sleeps longer than a bounded poll; time-based behaviour (expiry, lease) uses an injectable clock in `synthesis-orchestrator`.
- A criterion is not done until its tests ran on the platforms listed (CLAUDE.md "Cross-platform is a requirement").

## 4. Performance and recovery targets (from the design; hypotheses until measured)

| Target | Test | How measured | Pass rule |
|---|---|---|---|
| State change visible in under 1 s after commit | `perf_event_cursor_latency` (crate) | Time from commit to `events.subscribe` delivery in process | p95 < 1 s on CI hardware; informational on Windows |
| Policy decision under 50 ms p95 | `perf_gateway_authorize` (crate, criterion-style loop) | 10,000 calls with a cached envelope | p95 < 50 ms; log, do not fail the first release |
| Recovery of 100 work items and 10 pending effects under 10 s | `perf_recovery_100` (crate) | Seed DB, run recovery | < 10 s; log trend |
| No unbounded workers/tokens/memory with 1,000 queued items | `orch-parallel-cap` | counters | bounded |

These are initial hypotheses; failing them is a finding, not a gate, until the owner fixes numbers (plan section 7).

## 6. Mapping to existing CI

No new job is created. New Rust tests run in `test` (macOS, Ubuntu, Windows) and, with `--features synthesis-cli/test-provider`, in the same job step that already runs `apps/cli/tests`. New red-team cases are picked up by the `redteam` job (`node tests/redteam/run.mjs --strict-gaps`). `sandbox-linux` runs the bubblewrap-dependent cases. The `desktop` job gains tests only with PR-14 (TUI) and PR-15 (Super Agent). Nightly real-model evals (`evals-nightly.yml`) are unchanged; an outcome eval (real model, MVP scenario) is proposed after the MVP and must keep the existing cost caps.
